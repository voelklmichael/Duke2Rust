# Step 001 – Port the C code to 32-bit Linux

Goal: a native Linux build of Duke Nukem 3D, compiled with gcc **and** clang
using `-m32`, that runs the original game data. This gets the code ready for
c2rust (Step 002), which needs C that clang can compile for a Linux target.

Non-goals for this step: cleaning up the code, 64-bit support, networking, and
audio.

**Status:** done except audio. The game builds with gcc 13 and clang 18 and
is playable in an SDL2 window (keyboard and mouse), with no sound.
`compile_commands.json` for c2rust is generated by a script.

## Quick start

```sh
scripts/run_dos.sh --prepare-only   # once: unpack game data into build/run (see Step 000)
make -C port                        # gcc, SDL2 window   -> build/linux/duke3d
make -C port CC=clang               # same with clang
make -C port PLATFORM=null          # headless build, no SDL needed

cd build/run && ../linux/duke3d               # play
cd build/run && ../linux/duke3d /v1 /l1 /s2   # start E1L1 directly (options use '/', not '-')
```

Headless and automated runs:

- `SDL_VIDEODRIVER=dummy` runs the SDL build without a window.
- `DUKE_FRAMEDUMP=<dir>` writes every `DUKE_FRAMEDUMP_EVERY`-th frame
  (default 30) as a PPM file. Both platform layers support this.

c2rust input: `scripts/compile_commands.sh` writes `port/compile_commands.json`.

32-bit SDL2: `libsdl2-2.0-0:i386` (the runtime) is enough. If
`libsdl2-dev:i386` is installed, the Makefile uses it through pkg-config.
Otherwise it uses the regular SDL headers plus a shim for Debian's per-arch
config header, which is safe because its only arch-specific value,
`SIZEOF_VOIDP`, depends on `__LP64__`.

## Why 32-bit

The code assumes `sizeof(long) == 4` and `sizeof(void*) == 4` throughout:

- pointers are stored in `long` variables (`waloff[]`, `frameplace`,
  `palookup` offsets, ...)
- `.MAP`/`.ART`/savegame/demo data is read straight into structs made of `long`

With `-m32`, the code behaves as it did on DOS. c2rust will then produce
`c_long == i32` for the `i686-unknown-linux-gnu` target, which Rust fully
supports. Moving to 64-bit is cheaper later, once the code is in Rust.

Checked: the struct sizes match the file formats (sector 40, wall 32,
sprite 44 bytes). Watcom's default 32-bit packing is natural alignment, the
same as `gcc -m32`, so demo and savegame records also match.

## Layout

The original files under `duke_nukem_3d/` stay untouched, so the DOS build
from Step 000 keeps working as the reference.

```
port/
  Makefile            # gcc or clang, -m32 -> build/linux/duke3d
  game/               # Duke sources (lowercased, LF), patched
  engine/             # Ken's engine.c, cache1d.c, mmulti.c + a.c (replaces A.ASM)
  compat/             # pragmas.c (PRAGMAS.H in C), DOS/Watcom shims
  mact/               # MACT386.LIB reimplementation
  audio/              # FX_/MUSIC_ API (silent stubs for now)
  platform/           # platform_sdl.c (default), platform_null.c (headless)
```

The commit "Step 001: plan, import original sources into port/" contains the
unmodified sources. `git diff <that commit> -- port/game port/engine` shows
every porting change. In the original files, each change is marked with a
`// PORT:` comment.

## What was done

### Inline assembly → C

- **`PRAGMAS.H`** (~180 Watcom `#pragma aux` functions): `compat/pragmas.c`
  and a new `game/pragmas.h`, generated by a script because there are
  `mulscale1..32`, `divscale1..32` and so on. The results are bit-exact:
  64-bit intermediates truncated to 32 bits as `shrd`/`idiv` did, no signed
  left-shift UB, and `clearbufbyte`/`copybufbyte` reproduce the original
  store pattern. Address arguments go through macros that cast to `long`, so
  callers can keep passing pointers or integers.
- **Engine-local pragmas** in `engine.c` (`nsqrtasm`, `msqrtasm`,
  `krecipasm`, `getclipmask`, `setgotpic`): translated instruction by
  instruction.
- **`A.ASM`** (2,400 lines of self-modifying texture-mapping loops):
  `engine/a.c`. The patched constants became static variables. Each function
  documents its original register interface. Deliberate differences, all of
  which affect rendering only and never game state:
  - Several fast paths approximated the exact per-pixel stepping
    (`hlineasm4`'s 4-pixel loop, `vlineasm4`, `mvlineasm4`, `qrhlineasm4`).
    The C version always does the exact calculation, so floors may differ
    from DOS by an occasional texel.
  - A texture shift of 32 gives 0 instead of x86's "count mod 32".
  - The x87 1/z accumulator in `slopevlin` uses `double` instead of 80-bit.
- **Copy-protection checks:** two `getkensmessagecrc` checksum tests of a
  constant string were removed.

### Ken's 2000 engine instead of Duke's 1996 `ENGINE.OBJ`

Duke shipped only a prebuilt `ENGINE.OBJ`. The available source is Ken's
later release. Differences that needed handling:

- `validmode*` declarations were added to `BUILD.H`.
- `setgamemode()` only supports VESA (1), buffered 320×200 (2) and
  red/blue (6). Duke's config uses chained/Tseng/S3 modes. All modes now use
  one path: a single buffered 8-bit framebuffer handed to the platform layer.
- `ves2.h` (VESA BIOS and DPMI) was replaced by a short version that calls
  the platform layer for presenting frames and setting the palette.

### DOS/Watcom → Linux (`compat/`)

- Stand-ins for `dos.h`, `i86.h` (`int386` only logs), `conio.h`, `bios.h`,
  `io.h`, `process.h`.
- `_dos_findfirst`/`_dos_findnext` via `opendir` and `fnmatch`.
- `_bios_timeofday`, `stricmp`/`strupr`/`ltoa`, `filelength`, and `_argc`/`_argv`.
- **Case-insensitive file access:** `open`/`fopen`/`access` try the exact
  name, then a case-insensitive match, because the game asks for
  `tiles000.art`, `GAME.CON` and so on in mixed case. Backslashes in paths
  are converted.
- `min`/`max` macros (Watcom intrinsics), plus empty `far`, `interrupt` and
  `cdecl` keywords.

### MACT386.LIB (no source) → `mact/`

Written from the library's disassembly. Open Watcom's `wlib -x` extracted the
objects and `wdis` disassembled them.

- **`FindDistance2D`/`FindDistance3D`:** exact. They feed game logic.
- **`CONTROL_*`:** same data model and logic:
  - key and button mapping, toggle flags
  - analog→digital axes with hysteresis
  - axis scaling and clamping
  - mouse delta scaling (smaller axis /3, sensitivity 0x8000)
  - double-click timing

  Joystick and external controllers are not supported.
- **`KB_*`:** key-state array and character queue. The scancode name table
  and ASCII/shift tables were extracted from the library
  (`mact/kb_tables.h`). Scancodes are MACT's, with extended keys at
  0x5a–0x6d.
- **`SCRIPT_*`:** INI parser and writer for `DUKE3D.CFG` with the original
  semantics. A missing or `~` number leaves the value unchanged, `0x` means
  hex, and strings must be quoted (80 characters max). Comments are kept
  when saving.
- **Utilities and timer:** `Error`, `CheckParm`, `Safe*`, `file_lib`, and the
  task manager. The 120 Hz `totalclock` timer runs on a thread, asynchronous
  like the DOS timer interrupt.

### Platform layer (`platform/`)

On DOS, keyboard and timer were interrupt driven, and the game polls their
state in busy loops (`while (!KB_KeyWaiting()) ...`). To keep that model,
`platform_sdl.c` gives SDL its own thread. That thread handles window events,
translates SDL scancodes into MACT scancodes (`KB_KeyEvent`, like the
keyboard interrupt), accumulates mouse motion, and shows the most recent
frame. The frame is converted with the palette and shown at 4:3 in a
640×480 window. The game thread only hands over frames and palettes.
`platform_null.c` is the headless variant.

### Fixes to the original code

These are the kind of things the DOS toolchain tolerated:

- **Case-insensitive linking hid misspelled names:** `testcallback` →
  `TestCallBack`, `PlayMusic` → `playmusic`, `Shutdown` → `ShutDown`,
  `KB_GetCh` → `KB_Getch`, `KB_FlushKeyBoardQueue` →
  `KB_FlushKeyboardQueue`, and `Music_SetVolume` → `MUSIC_SetVolume`.
- **Writes into string literals:** `char *fn = "game0.sav"; fn[4] = ...`,
  9 places, became arrays.
- **Wrong argument count:** two `kread(...)` calls with a stray fourth
  argument.
- **Header ordering:** `struct player_struct` was used in `funct.h` before
  its definition, `#include <fcntl.H>` had the wrong case, and a few game
  functions used without declarations got prototypes at the end of
  `duke3d.h`.
- **Implicit declarations** (needed for clang 18 and for c2rust):
  - All engine functions now have prototypes (`engine/engine_protos.h`,
    generated with `gcc -aux-info`).
  - 170 definitions without a return type got one: `void` (104) if they
    never return a value, otherwise `int` (66).

## Verification so far

- **Title, logo animation and main menu:** identical to DOSBox screenshots of
  the original DOS build.
- **E1L1:** renders correctly with both the gcc and the clang build. That
  covers walls, floors, the parallax sky, masked and sloped surfaces,
  sprites, the weapon and the status bar.
- **Input:** walking and turning work with keyboard input in the SDL window.

The demos shipped in `3D_duke3d.zip` don't play in either build. Their
version byte is 1, but this source expects `BYTEVERSION` 116. So they are
data from another version, not a porting bug; the original DOS build also
skips them.

## Open points / next steps

- **Audio:** sound effects via SDL audio, reusing the VOC/WAV and mixer logic
  from `AudioLib.zip`. Music (MIDI) later.
- **Determinism harness for Step 002 and later:** record a demo with this
  build (`/r` option), then log a game-state hash per tick during playback.
  That gives the objective comparison between the C port and the Rust
  version.
- **Compiler warnings:** they are still suppressed (`-w`), and there are many.
  Worth cleaning up gradually, especially before relying on c2rust output.
- **Missing features:** no joystick, no network play (`mmulti` is
  single-player only), and the 2D editor drawing functions are unused stubs.
